# 1. PROBLEM

Mission operators deal with large amounts of:

* Telemetry
* Mission logs
* Procedures
* Historical incidents
* Technical information

When an anomaly occurs, operators need to quickly determine:

* What happened?
* When did it happen?
* Which subsystem is affected?
* What evidence supports the observation?
* Has something similar happened before?
* Which procedure applies?
* What should be investigated next?

The system must help operators investigate anomalies while preserving evidence and human oversight.

---

# 2. CORE PRODUCT

Build:

> **Mission Operations Copilot with Evidence-Grounded Decisions**

The copilot must:

* Accept or identify a mission anomaly.
* Retrieve relevant telemetry.
* Retrieve relevant mission logs.
* Retrieve applicable procedures.
* Retrieve similar historical incidents.
* Correlate events over time.
* Explain the anomaly.
* Show supporting evidence.
* Suggest diagnostic steps.
* Generate an auditable timeline.
* Record the investigation in an audit trail.
* Clearly distinguish facts from AI-generated recommendations.

The AI is an **operator assistant**, not an autonomous controller.

---

# 3. NON-NEGOTIABLE SAFETY RULE

The system must NOT:

* Send spacecraft commands.
* Execute spacecraft commands.
* Connect to real spacecraft.
* Connect to real mission-control systems.
* Control hardware.
* Request real spacecraft credentials.
* Perform autonomous mission actions.

Every action is simulated.

Display prominently:

> **SIMULATION / DECISION SUPPORT ONLY**

And:

> **AI recommendations require operator review.**

---

# 4. EVIDENCE-GROUNDED AI

This is the central feature.

Every important AI claim must be supported by retrieved evidence.

The AI must distinguish:

### OBSERVED FACT

Directly supported by mission data.

### EVIDENCE

The actual telemetry/log/procedure/incident supporting the statement.

### INFERENCE

Reasoning derived from evidence.

### RECOMMENDATION

Suggested diagnostic action.

### CONFIDENCE

Confidence associated with the inference/recommendation.

### LIMITATIONS

What the system cannot establish from the available evidence.

---

# 5. EXAMPLE OF CORRECT OUTPUT

For an abnormal battery temperature:

### Observed Facts

* Battery current increased from 15.8A to 18.7A.
* Battery temperature increased by 8°C.
* FDIR generated a power subsystem warning.

### Evidence

* `TEL-4821`
* `TEL-4830`
* `LOG-223`
* `PWR-204`
* `INC-102`

### Inference

> Elevated power consumption may be contributing to the observed battery temperature increase.

### Recommendation

> Check battery load and compare current draw against the expected operating range.

### Confidence

> 82% — Medium/High

### Limitation

> Available data does not establish definitive root cause.

Never convert an inference into an unsupported fact.

---

# 6. FAILURE BEHAVIOR

If evidence is insufficient, the system must say:

> **INSUFFICIENT EVIDENCE**

> The available mission data does not provide enough evidence to determine the root cause. Additional telemetry or operator investigation is required.

Never force the LLM to produce an answer.

"Unknown" is preferable to hallucination.

# 15. EVIDENCE ENGINE

Every retrieved item must contain:

* Source type
* Document ID
* Timestamp
* Subsystem
* Relevant text/value
* Relevance score

```text

ID: TEL-4821

SUBSYSTEM: POWER

Battery Current = 18.7 A

```

Evidence IDs must be usable by the UI.

Clicking an evidence citation must open its underlying record.

# 16. EVIDENCE VALIDATION

Before displaying an AI response:

1. Extract cited evidence IDs.
2. Verify each ID exists.
3. Verify the evidence was actually retrieved.
4. Reject invalid citations.
5. Prevent unsupported claims from being presented as evidence-backed.

The system must never fabricate source IDs.
